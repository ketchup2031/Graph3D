# Graph3D — план разработки

> **Статус:** начальный план  
> **Горизонт:** ноябрь 2026 — май 2027  
> **Режим работы:** примерно 1–2 часа в день  
> **Цель к защите:** работающий демонстрационный CAD-прототип и публичный релиз `v0.1.0`  
> **Долгосрочная цель:** развить проект в самостоятельную Open Source CAD-систему для механического проектирования.

---

## 1. Видение проекта

**Graph3D** — кроссплатформенная параметрическая CAD-система для создания трёхмерных механических деталей и инженерной документации.

Проект вдохновлён функциональностью профессиональных CAD-систем, включая КОМПАС-3D, FreeCAD и SolidWorks, но должен иметь собственную реализацию, архитектуру, интерфейс и визуальную идентичность.

### Основные принципы

1. Геометрическая корректность важнее количества функций.
2. Модульная архитектура с чёткими границами ответственности.
3. Разделение пользовательского интерфейса, модели документа и геометрического ядра.
4. Воспроизводимые сборки и автоматические тесты.
5. Открытая разработка: задачи, документация, история изменений и релизы доступны в GitHub.
6. Никакого копирования закрытого исходного кода, ресурсов или защищённых элементов интерфейса коммерческих CAD-систем.

## 2. Цели и границы первого релиза

### Цель `v0.1.0`

К маю 2027 года подготовить приложение, в котором пользователь сможет:

- создать новый документ;
- просматривать 3D-сцену и управлять камерой;
- создавать базовые эскизы;
- строить простые твёрдые тела;
- выполнять несколько базовых операций над телами;
- видеть историю построения модели;
- изменять параметры поддерживаемых операций;
- сохранять и открывать собственный формат проекта;
- экспортировать модели в STEP и STL;
- продемонстрировать создание одной законченной механической детали.

### Обязательный функциональный минимум

| Модуль | Минимальный результат |
|---|---|
| GUI | Главное окно, меню, панели и строка состояния |
| Viewport | Вращение, панорамирование, масштабирование, стандартные виды |
| Sketcher | Линии, окружности, прямоугольники |
| Part Design | Выдавливание и вращение профиля |
| Geometry | Базовые операции OCCT и проверка результата |
| Feature Tree | Отображение истории построения |
| Properties | Просмотр и изменение параметров поддерживаемых операций |
| Document | Создание, сохранение и открытие проекта |
| Import/Export | Экспорт STEP и STL; импорт STEP — если останется время |
| Tests | Автоматические тесты ключевой логики |

### Не входит в обязательства первого релиза

Следующие функции не должны задерживать `v0.1.0`:

- полноценный решатель геометрических ограничений;
- сложные сборки и кинематические связи;
- листовой металл;
- CAM и CAE;
- полноценная система плагинов;
- полная поддержка ЕСКД;
- совместимость с внутренними форматами КОМПАС-3D;
- полная замена КОМПАС-3D или FreeCAD.

Эти возможности рассматриваются как направления развития после первого релиза.

## 3. Технологический стек

| Область | Технология | Назначение |
|---|---|---|
| Язык | C++20 | Основная логика |
| GUI | Qt 6 | Окна, меню, панели, взаимодействие |
| Геометрическое ядро | Open CASCADE Technology (OCCT) | B-Rep, геометрические операции, CAD-обмен |
| Сборка | CMake | Конфигурация и сборка |
| Генератор | Ninja | Быстрая сборка |
| Контроль версий | Git | История изменений |
| Хостинг | GitHub | Репозиторий, Issues, Releases |
| Тестирование | Catch2 или GoogleTest | Модульные тесты |

### Правила выбора зависимостей

- Перед добавлением библиотеки проверить её лицензию, совместимость с выбранными версиями Qt и OCCT, активность проекта и доступность на Windows/Linux.
- Не добавлять зависимость ради одной небольшой функции без обоснования.
- Зафиксировать версии или безопасные диапазоны версий зависимостей.
- Вести `THIRD_PARTY_NOTICES.md`.
- До публикации релиза проверить совместимость лицензий всех библиотек и способ распространения Qt.
- Не заявлять о совместимости с коммерческими CAD-форматами, пока она не проверена тестовыми файлами.

## 4. Предлагаемая архитектура

Архитектура должна быть модульной. GUI не должен напрямую содержать геометрические алгоритмы или управлять внутренними объектами OCCT во всех частях приложения.

### Логические слои

1. **Application** — запуск приложения, конфигурация, жизненный цикл.
2. **GUI** — главное окно, меню, панели, диалоги и действия пользователя.
3. **Command System** — команды, проверки входных данных и выполнение операций.
4. **Document Model** — документы, объекты, свойства и история построения.
5. **Sketcher** — двумерная геометрия и редактирование эскизов.
6. **Part Design** — последовательность операций построения деталей.
7. **Geometry Adapter** — изолированный слой взаимодействия с OCCT.
8. **Viewport** — отображение геометрии и управление камерой.
9. **Import/Export** — чтение и запись поддерживаемых форматов.
10. **Tests** — тесты независимых модулей и интеграционные сценарии.

### Ключевые архитектурные требования

- Геометрические типы OCCT не должны бесконтрольно распространяться по GUI-коду.
- Документная модель должна хранить объекты и параметры операций, а не только готовую визуальную геометрию.
- Каждая операция должна иметь проверяемые входные параметры и понятный результат или ошибку.
- Перестроение модели должно быть детерминированным для одинакового документа и одинаковой версии ядра.
- Ошибка одной операции не должна молча приводить к сохранению некорректного результата.
- Сохранение проекта должно быть версионируемым, чтобы формат можно было развивать.
- Не создавать собственный геометрический kernel в рамках первого релиза.

### Этап 14. Редактируемые параметрические эскизы

## 6. Демонстрационный сценарий для защиты

Основной демонстрационный объект — механический фланец с центральным отверстием и крепёжными отверстиями.

Предлагаемая последовательность:

1. Создать новый документ.
2. Создать эскиз фланца.
3. Построить основное тело выдавливанием.
4. Создать центральное отверстие.
5. Создать крепёжные отверстия.
6. Показать дерево построения.
7. Изменить один параметр и продемонстрировать перестроение модели.
8. Сохранить проект.
9. Экспортировать модель в STEP или STL.
10. Показать ортогональные проекции, если чертёжный модуль готов.

Не следует включать в презентацию функции, которые существуют только как макеты интерфейса или не проходят проверку.

## 7. Критерии качества

Целевые ориентиры к защите:

- не менее 10 законченных пользовательских действий/инструментов;
- не менее 5 типов геометрических операций или построений, если они реализованы и протестированы;
- собственный формат проекта;
- экспорт STEP и STL;
- 3 демонстрационные модели;
- автоматические тесты ключевых модулей;
- инструкции сборки и запуска;
- отсутствие известных блокирующих ошибок в основном демонстрационном сценарии.

Количество тестов само по себе не является показателем качества. Важнее проверять реальные граничные случаи и корректность геометрии.
